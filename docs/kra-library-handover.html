Part 1What the feature is

HR publishes a shelf of suggested KRAs per job title, once. Every employee holding that title then picks from their own role's shelf when writing their KRAs, instead of being emailed a spreadsheet.

It sits alongside the KRA importer that already exists. The two are different on purpose, and confusing them is the single most common support question on this feature — a designation-keyed file uploaded on the employee-keyed screen is the exact mistake that prompted this document.

Uploading a file on the wrong screen is refused with a message naming the right one, in both directions. That check lives in validateKraBulkRows.

What ships

Database — one migration

server/migrations/033-kra-library.js creates one table and one index. It alters nothing that already exists.

-- pms.kra_library
id               uuid PRIMARY KEY DEFAULT gen_random_uuid()
tenant_id        uuid NOT NULL
designation      text NOT NULL
category         text            -- the sheet's "Parameters" column
title            text NOT NULL   -- the KRA
measures         text            -- the KPIs
description      text            -- Comments
suggested_weight numeric(6,2)
sort_order       integer NOT NULL DEFAULT 0
uploaded_by      text
uploaded_at      timestamptz NOT NULL DEFAULT now()

CREATE INDEX kra_library_designation_idx
  ON pms.kra_library (tenant_id, lower(btrim(designation)), sort_order);

Three decisions someone will otherwise undo by accident:

  • No cycle_id. The library is reference data about roles, not about a year. Scoping it to a cycle would mean re-uploading every shelf each time HR opens one — which is most of the work this removes.
  • No unique constraint, no ON CONFLICT. A re-upload is a delete-then-insert per designation in one transaction. That is the only way to express “this designation now has exactly these six KRAs, and the seventh is gone”, and it is why correcting one role never disturbs another.
  • The index is on lower(btrim(designation)) because the designation on an employee record and the one typed into a spreadsheet differ by case and stray spaces. To an employee, a shelf that silently fails to match is indistinguishable from a shelf that is empty.

Tests

server/test/kra-library.test.js — 17 tests, pure: they build real .xlsx buffers and drive the parser directly, no database and no HTTP. Three of them are load-bearing:

  • “A SHELF DOES NOT HAVE TO TOTAL 100” — if this starts failing, the library has been made to behave like an assignment and the feature is pointless.
  • “the same file keyed by employee_email still enforces 100” — the control. If this stops failing, the library's leniency has leaked into the importer that must not have it.
  • “the Parameters carry stops at a designation boundary” — pins a real bug found in the client's own 2,145-row file, where 235 KRAs across 14 designations silently inherited the previous role's Parameter.

Run the whole suite against a real PostgreSQL before deploying:

createdb apms_check
cd server
DATABASE_URL="postgres://USER:PASS@127.0.0.1:5432/apms_check" \
  DATABASE_SSL=false JWT_SECRET=x TENANT_SLUG=x npm test
# expect: # pass 414 / # fail 0

DATABASE_SSL=false is required for a local PostgreSQL. Without it the pool attempts TLS against a server that never offered it, and every test fails to connect.

Part 2Deploying the code

Pick the path matching how the instance runs. In all three the migration runs itself on the next boot — there is nothing to execute by hand.

One command

sudo /opt/agentic-pms/deploy/service/update.sh

It takes a backup first, fetches, fast-forward pulls, reinstalls, rebuilds the frontend, rsyncs into the web root only after the build succeeds, restarts the API and health-checks it for 90 seconds. It does not touch the environment file.

Confirm the migration ran

sudo journalctl -u agentic-pms-api -n 50 --no-pager | grep migration
# migration 033-kra-library.js: done

The installer deliberately never overwrites /etc/agentic-pms/api.env on a re-run, so your API key and secrets survive an update.

Rebuild and recreate

cd /opt/agentic-pms/deploy/docker
git -C /opt/agentic-pms pull
docker compose build && docker compose up -d
docker compose logs api | grep migration

Environment comes from the .env file beside the compose file — see deploy/docker/.env.example for the full list.

Merging is the deploy

git fetch origin
git checkout main
git merge --ff-only origin/<feature-branch>
git push origin main

Then watch both services in the dashboard. agentic-pms-api runs the migration during boot — look for migration 033-kra-library.js: done; if it crash-loops, read the migration error, because a failed boot is the safety mechanism. agentic-pms-frontend is a static rebuild; the asset hash changing is how you know it landed.

Check auto-deploy is actually on

This has already caught us out: a push reached main and nothing happened, because auto-deploy was off on both services. The site served a two-week-old build with no error anywhere. Verify from outside rather than assuming:

BUNDLE=$(curl -s https://<frontend-host>/ | grep -oP 'src="\K/assets/[^"]+\.js' | head -1)
curl -s "https://<frontend-host>$BUNDLE" | grep -c "Choose from library"
# 0 means the old bundle is still being served
Free tier is not durable

On Render's free plan the API sleeps after 15 minutes idle, and the database is removed at the end of its trial window with no backup and no restore path. Fine for a PoC on disposable data. Move to a paid tier before any real employee record goes in.

Verifying the migration landed

SELECT * FROM core.migrations_log WHERE filename LIKE '033%';
SELECT count(*) FROM pms.kra_library;   -- 0 on a fresh deploy
\d pms.kra_library

Part 3Switching the AI assistance on

If an instance shows “Agentic features are not configured on this instance (ANTHROPIC_API_KEY missing)”, that is the product behaving correctly, not a fault. One environment variable turns it on.

The key never goes in git

Not in render.yaml, not in a committed .env, not in a Dockerfile, not in this document. The repository is public. A key that reaches a commit is burned and must be revoked, not deleted — the history keeps it. Everywhere below, sk-ant-… is a placeholder; paste the real value only into the store named.

DeploymentWhere the key goes
systemd/etc/agentic-pms/api.env → ANTHROPIC_API_KEY=sk-ant-…, then sudo systemctl restart agentic-pms-api. File is root:apms 0640; never loosen that.
Dockerdeploy/docker/.env → ANTHROPIC_API_KEY=sk-ant-…, then docker compose up -d. That file is gitignored — keep it so.
RenderDashboard → the agentic-pms-api service → Environment. render.yaml already declares it with sync: false, which is what keeps the value out of git and preserves it across Blueprint syncs.

The second variable

AI_MODEL selects the model. It is not a secret and belongs in version control. The code falls back to claude-sonnet-4-5 if it is unset, which is a generation behind — both render.yaml and the systemd installer set claude-opus-5. The request body is plain model / max_tokens / system / messages, so a newer model is drop-in with no code change.

What the key turns on

21 endpoints under /api/v1/agentic — drafting help for the self-appraisal, mid-year review, development plan, career aspiration, calibration brief, closure letter, appraisal summary and the HR-only parameter analysis.

What it is not allowed to do

The house rule is deterministic numbers, AI narrates, enforced at the single entry point in server/core/ai.js. No AI call can produce a rating, score or distribution; stripRatingSuggestions() removes rating-shaped keys from structured output as a second line of defence. Every number in the product — weights, ratings, weighted averages, increment costs — is computed by the application from the data. If a change makes a number depend on a model reply, that change is wrong.

The key is read server-side only, sent as the x-api-key header to api.anthropic.com. It never reaches the browser — there is no reference to it anywhere in frontend/src.

Confirming it works

TOK=$(curl -s -X POST "$B/auth/dev-login" -H 'Content-Type: application/json' \
  -d '{"email":"<hr-admin>","password":"<password>"}' | jq -r .token)

curl -s -X POST "$B/agentic/devplan-suggest" \
  -H "Authorization: Bearer $TOK" -H 'Content-Type: application/json' -d '{}' \
  | jq '{ok, goals: (.draft.suggested_goals | length)}'

# {"ok": true, "goals": 9}   -> the key is live
# HTTP 503                   -> still not configured; restart after editing the env

Part 4Publishing the library

Once the code is live this is HR's job, through the screen. Document it for them rather than doing it for them.

  1. HR Admin → KRA LibraryThe nav entry only appears for admin and hr roles.
  2. Choose the workbookDesignation-keyed. Every worksheet is read, so a multi-tab role workbook publishes in one go.
  3. ValidateA dry run. Nothing is written. Read the report.
  4. PublishOnly enabled once the dry run passes.

The upload format

ColumnReq.Notes
DesignationYesDesignations, Job Title, Role and their plurals also accepted. Written once above a block carries down it.
ParametersNoFinancial / Project / Process / Customer / People. Carries down within its own designation block only. Stored as category.
KRA (S.M.A.R.T GOALS)YesStored as title.
KPIs (Measuring Metrics & Data Source)NoStored as measures.
Suggested WeightageYesWeightage and Weight also accepted. Positive number.
CommentsNoStored as description.

Header matching ignores case, punctuation and parenthesised qualifiers, so KRA \n(S.M.A.R.T GOALS) and kra both resolve. An unrecognised column is an ignored-column warning, not an error.

Reading the report

  • Errors block the publish and name the sheet and row.
  • A designation nobody holds is a warning, not an error — HR builds shelves ahead of hiring.
  • employees per shelf is the number that decides whether a shelf does anything. Zero means published and unreachable — almost always the designation is spelt differently here than on the employee records. Shown in amber for that reason.
  • “Designations with no shelf yet” lists what is left, ordered by how many employees it affects.

Publishing replaces the shelf for each designation in the file and leaves every other designation untouched. KRAs employees have already picked are copies on their own sheets — revising the library never rewrites a KRA somebody has agreed with their manager.

Part 5Verifying end to end

B=https://<host>/api/v1
TOK=$(curl -s -X POST "$B/auth/dev-login" -H 'Content-Type: application/json' \
  -d '{"email":"<hr-admin>","password":"<password>"}' | jq -r .token)

# 1. Dry run — expect ok:true, errors 0
curl -s -X POST "$B/pms/hr/kra-library/upload" -H "Authorization: Bearer $TOK" \
  -F "file=@Mindgate_KRA_Library.xlsx" | jq '{ok, summary}'

# 2. Publish
curl -s -X POST "$B/pms/hr/kra-library/upload?commit=1" -H "Authorization: Bearer $TOK" \
  -F "file=@Mindgate_KRA_Library.xlsx" | jq '{ok, committed, summary}'

# 3. Coverage — how many employees will actually see a dropdown
curl -s "$B/pms/hr/kra-library" -H "Authorization: Bearer $TOK" | jq '{
  shelves:           (.shelves | length),
  reaching_someone:  ([.shelves[] | select(.employees > 0)] | length),
  employees_covered: ([.shelves[].employees] | add),
  uncovered:         [.uncovered[] | {designation, employees}]
}'

Then confirm the last mile without minting a login for a real employee — the HR-side endpoint resolves any employee's shelf:

curl -s "$B/pms/team/kra-library/<employeeId>" -H "Authorization: Bearer $TOK" \
  | jq '{designation, offered: (.entries | length)}'

In the interface the employee should see a banner reading “Start from the <designation> KRA library” on My KRAs, and Choose from library should open a pick list grouped by Parameter with a running total in the footer.

If no banner appears at all, the shelf exists but the strings do not match:

SELECT e.designation, count(*) AS employees,
       EXISTS (SELECT 1 FROM pms.kra_library l
                WHERE l.tenant_id = e.tenant_id
                  AND lower(btrim(l.designation)) = lower(btrim(e.designation))) AS has_shelf
  FROM core.employees e
 WHERE e.tenant_id = '<tenant uuid>' AND e.status = 'active'
 GROUP BY 1, 3 ORDER BY has_shelf, employees DESC;

Part 6Rolling back

The feature is additive, so reverting the code is enough — the table can stay where it is, because nothing else reads it.

# Newest first, or the two reverts conflict with each other.
git revert --no-commit cc0c23d 1e57582 07fcd01 && git commit && git push origin main

There is no down migration, by design: migrations in this codebase only go forward, and a failed boot is the safety net. If the table genuinely has to go:

DROP TABLE IF EXISTS pms.kra_library;
DELETE FROM core.migrations_log WHERE filename = '033-kra-library.js';

Dropping it does not affect any KRA an employee has already picked — those are copies in pms.kras.

Part 7Things that have already cost us time

None of these is guessable from the code. Each one was found the hard way.

  • DATABASE_SSL=false is required for a local or same-host PostgreSQL. Without it every connection attempts TLS and the boot dies on an error that reads like a bad password.
  • VITE_API_URL must stay UNSET on a single-host deployment. The frontend builds https://${VITE_API_URL}/api/v1 when set and a plain /api/v1 when not. Behind nginx on one box the relative path is what you want. It is also build-time — changing it needs a frontend rebuild, not a restart.
  • AUTH_DEV=true is currently the only working sign-in path. OIDC is scaffolded, not implemented. Set it to false and nobody can log in, including the administrator.
  • Legacy .xls is refused deliberately. The only maintained parser for it ships unpatched high-severity advisories. Re-save as .xlsx.
  • A .xlsx carrying cell comments can fail the import. Known, not yet fixed. Save a copy without comments.
  • npm test must run serially. The suite shares one database; run in parallel it produces a different set of phantom failures every time. The script already sets --test-concurrency=1 — do not remove it.
  • Never add title as an alias for the designation column. In these sheets that word means the KRA's own title far more often than the job title, so it would file every KRA under a designation named after itself. A test pins this.
  • A helper tab whose headers look like a KRA table gets read as one and fails the upload. Keep the words “KRA” and “Weightage” out of any notes sheet in an upload workbook.
