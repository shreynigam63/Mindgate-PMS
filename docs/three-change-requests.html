Request 1Approved goals stop being editable when the cycle moves on

Confirmed defect No migration Backend + one line of UI

What happens today

The phase machine grants development-plan editing to exactly one phase (server/modules/performance/phase-machine.js):

const ALLOWS = {
  kra_open:        ['kra_edit', 'kra_submit', 'kra_decide'],
  growth_planning: ['devplan_edit', 'devplan_submit', 'devplan_decide', 'career_edit'],
  mid_year_review: ['midyear_self_edit', …],      // devplan_edit is not here
  …
};

I put a cycle into Mid-Year Review with an approved plan and called the real endpoints as the employee. Verbatim:

-- A. edit a goal's text
PUT /pms/my/development-plan/goals
  409 {"error":"Development plan editing is not open (phase: mid_year_review)"}

-- B. record progress on the same goal
PUT /pms/my/development-plan/goals/<id>/progress
  200 {"ok":true,"progress_pct":55}

-- C. the same edit, after HR returns the plan to draft
PUT /pms/my/development-plan/goals
  409 {"error":"Development plan editing is not open (phase: mid_year_review)"}

Three things follow, and the third is the one that costs you time:

  • Progress already works after the phase moves (B). The sliders on My Growth keep working all year — that part is by design and is not what is broken.
  • Goal text, target dates, and adding a goal are blocked (A) the moment HR advances past Growth Planning.
  • Returning the plan does not unblock it (C). The phase check runs before the status check, so HR's normal remedy — return the plan to the employee — has no effect. The only remaining lever is rolling the whole cycle back, which moves every employee in the company backwards to let one person fix one goal.
This is the real cost

A cycle rollback is an all-tenant action. Using it as the routine way to edit one goal is what the client is describing, and they are right that it is not the intended behaviour.

What I propose

Keep the intent of the original design — scope is agreed once, in Growth Planning — but stop using a company-wide rollback as the escape hatch. Two changes, both in modules/performance:

  1. Let a returned plan be edited in any phase up to Calibration. The phase gate stops applying once a manager or HR has deliberately returned the plan — the return is the authorisation. An approved or submitted plan stays locked exactly as it is now.
  2. Give the manager a "Return for edits" control on the plan itself, next to Approve. It exists for KRA sheets already; the development plan has the endpoint but no button outside Growth Planning.

Net effect: the employee who needs to revise a goal in November asks their manager, the manager clicks Return, the employee edits and re-submits. No rollback, nobody else affected.

Decision needed

If you would rather goals stay freely editable all year with no return step at all, that is a smaller change — add devplan_edit to the later phases and stop there. It is simpler, but it means a goal can be rewritten after the mid-year conversation has already been held against it. Say which you want; I have built neither yet.

Request 2A department dropdown for the KRA Library

New capability 1 migration, additive New HR settings screen

The bottleneck, measured

From the employee master loaded into the client instance:

Active employees1,398the population a shelf has to serve
Departments34the dimension the library cannot see today
Distinct job titles90the only key the library has
Titles spanning more than one department37every one of these is ambiguous

The worst offenders are exactly the generic titles: Manager appears in 15 departments, Senior Manager in 15, Assistant Vice President in 13, Senior Software Analyst in 10 across 146 people. One shelf called "Manager" has to serve a manager in Development and a manager in Human Resources at the same time. That is the bottleneck.

What I propose

Three pieces, in the order they would be built:

  1. A nullable department column on pms.kra_library (migration 034, additive, nothing existing altered). The upload sheet gains an optional Department column next to Designation.
  2. Most-specific-wins matching. An employee sees the shelf for their department + title if one exists; otherwise the shelf for that title with the department left blank. Every shelf already published keeps working untouched — they all have a blank department, which is now the fallback rather than the only option.
  3. A department dropdown on the HR KRA Library screen and on the employee's picker, sourced from the departments actually present in the employee master — no list to maintain by hand.
On "enable it in the system configuration"

Two tables for this already exist and are worth knowing about before anything new is invented. core.admin_settings (tenant_id, key, value jsonb) is real and in use — for exactly one key, the mail send mode — with no screen behind it. pms.dropdown_options exists and is completely unused: no code reads or writes it.

So: store the switch as kra_library_scope in core.admin_settings — designation (today's behaviour, the default) or department+designation — and build the small HR Admin → Settings screen that is missing. That screen is the actual new surface here, and it gives the mail mode a home too. If HR later wants to curate the department list by hand rather than derive it, pms.dropdown_options is where it belongs.

Request 3Associate the growth path with the KRA

Sequencing already enforced Association discarded 1 migration, additive

Half of this is already true

The ordering is already enforced by the phase machine. The phase order is kra_open → growth_planning → …, KRA editing is granted only in kra_open, and development-plan editing only in growth_planning. The growth path cannot be written before KRAs are locked — that is what the Growth Planning phase was added for.

What is missing

The association. The AI already works out which KRA each suggested goal serves, and the picker groups the suggestions under KRA headings — you can see it in the screenshots from earlier today. But pms.development_goals has no column for it:

CREATE TABLE pms.development_goals (
  id, tenant_id, plan_id,
  title, description, target_date,
  progress_pct, sort_order
  -- no kra_id, no serves_kra
)

So the link is computed, shown once in the popup, and thrown away the moment the goal is saved. Nothing downstream — the manager's view, mid-year, the appraisal summary — can say which KRA a development goal was meant to support.

What I propose

  • kra_id uuid and serves_kra text on pms.development_goals (migration 035, both nullable, nothing existing altered). The id is the real link; the text preserves the KRA title as it stood when the goal was written, so the association survives the KRA being edited or the cycle closing.
  • Store what the AI already produced when a suggestion is accepted — today that value is simply dropped.
  • A "Serves KRA" selector on every manually written goal, listing that employee's own approved KRAs for the cycle, plus a "Not tied to a KRA" option, which stays legitimate.
  • Group the saved goals by KRA on My Growth and on the manager's view of the plan, the same grouping the suggestion popup already uses.

Today the saved goals are a flat list with no KRA heading and no selector — the grouping exists only inside the AI suggestion popup, before anything is saved.

What this unlocks later

Once the link is stored, "which KRAs has this person built capability against?" becomes a query rather than a guess — on the manager's view, in the appraisal summary, and in the mid-year conversation. None of that is in scope here; it is simply not possible at all until the column exists.
