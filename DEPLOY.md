# Agentic PMS — PoC Deployment Runbook

Everything needed to stand this application up in a fresh Render account
and get to a working login. Written against the repository as it is; every
command and endpoint below was read out of the code, not from memory.

**Audience:** whoever is doing the deploy. No prior knowledge of this
codebase assumed.

**Time:** about 30 minutes, most of it waiting for builds.

> **Deploying to EC2 instead of Render?** Use
> [`deploy/README.md`](deploy/README.md) — a single instance with
> PostgreSQL on the same box, runnable either as a systemd service or
> under Docker. Sections 4 (first-run setup) and 7 (AI features) of this
> document still apply unchanged; the rest is Render-specific.

---

## 1. What you are deploying

Three resources, defined in `render.yaml` at the repository root. Render
creates all three from that one file.

| Resource | Type | What it is |
|---|---|---|
| `agentic-pms-api` | Node web service | Express API. Runs `node index.js` from `server/` |
| `agentic-pms-frontend` | Static site | React SPA. Built with Vite from `frontend/`, served from `dist/` |
| `agentic-pms-db` | Postgres | The only datastore. Also holds uploaded file bytes |

Node 22 (`engines` in both `package.json` files). No Redis, no object
storage, no mail server, no queue.

**One instance = one tenant.** Every row in the database carries a
`tenant_id`, resolved once at boot from `TENANT_SLUG`. If you need a
second client, deploy a second instance — do not try to share one.

## 2. Decide these before the first sync

Two values are effectively one-shot. Getting them wrong is recoverable but
annoying.

### `TENANT_SLUG` — set once, never change

`server/index.js` resolves this on boot and, on an empty database, creates
the `core.tenants` row from it. Changing it later **does not rename
anything** — it silently resolves to a *different* tenant, the app comes up
completely empty, and the original data is still in the database under the
old slug.

Edit `render.yaml` before syncing:

```yaml
- key: TENANT_SLUG
  value: mindgate        # ← change to the client's slug
```

### Database plan

`render.yaml` ships with `plan: free`. **Render allows only one free
Postgres per workspace.** If the workspace already has one, the sync fails
with:

> cannot have more than one active free tier database

Either free the existing one, or change the plan:

```yaml
databases:
  - name: agentic-pms-db
    plan: basic-256mb     # roughly $6-7/month, does not expire, is backed up
```

Read §8 before choosing free.

## 3. Deploy

1. Push this repository to a Git host Render can reach. Note the **branch**
   — `render.yaml` pins none, so Render builds the repository's **default
   branch**. If you work on a feature branch, nothing deploys until it is
   merged into the default branch.
2. In Render: **New → Blueprint**, select the repository, apply.
3. Render prompts for `ANTHROPIC_API_KEY` (declared `sync: false`, so its
   value is never in git). Leave it blank if you are not demonstrating the
   AI features — see §7.
4. Wait for all three resources to go green. The database is created first;
   `DATABASE_URL` is wired into the API automatically via `fromDatabase`,
   and `JWT_SECRET` is generated by Render. Neither needs a human.

### The one manual step

`VITE_API_URL` in `render.yaml` is a hardcoded literal, and it will be
wrong for your deployment:

```yaml
- key: VITE_API_URL
  value: agentic-pms-api-cx2k.onrender.com   # ← this deployment's hostname
```

Render appends a random suffix when a service name is already taken
globally, so the API hostname **cannot be predicted** from the service name
— it can only be read off the API service after the first sync.

1. Open the `agentic-pms-api` service in Render and copy its `.onrender.com`
   hostname (no `https://`, no trailing slash).
2. Put that value in `render.yaml`, commit, push.
3. Let the frontend rebuild.

This is **build-time**, not runtime — Vite inlines it into the JavaScript
bundle. Changing it in the Render dashboard alone does nothing; the static
site must rebuild.

Until this is right, every API call from the browser fails with
`net::ERR_NAME_NOT_RESOLVED` and the app looks completely broken.

### Confirm the API is up

```bash
curl https://<your-api-host>/api/v1/health
# {"ok":true,"service":"agentic-pms"}
```

All 32 migrations in `server/migrations/` run automatically at boot, in
filename order. **A migration failure fails the boot** — deliberately, so a
half-migrated schema can never serve traffic. If the API will not start,
read its Render logs before anything else.

## 4. First-run setup

Nothing below needs a database client. All of it is either one `curl` or a
screen in the app.

### 4.1 Create the first administrator

A fresh tenant has zero employees, so nobody can log in to create the first
account. One unauthenticated endpoint solves that, and it **locks itself
out permanently** the moment any employee exists.

Check it is available:

```bash
curl https://<your-api-host>/api/v1/setup/status
# {"bootstrap_available":true}
```

Create the admin. **Choose your own password** — minimum 8 characters. It
is bcrypt-hashed before the response is sent, never logged and never
returned:

```bash
curl -X POST https://<your-api-host>/api/v1/setup/bootstrap-admin \
  -H 'Content-Type: application/json' \
  -d '{"name":"Your Name","email":"you@company.com","password":"CHOOSE-YOUR-OWN"}'
```

If this returns `403 This tenant already has employees`, the tenant is not
fresh — someone already bootstrapped it. Ask them for access; there is no
second bootstrap.

### 4.2 Log in

Open the frontend URL and sign in with that email and password.

> Login works because `AUTH_DEV="true"` in `render.yaml`. That is the only
> login route that exists — real SSO/OIDC was never built. See §9.

### 4.3 Load employees

**People Hub → Directory**, or `POST /api/v1/employees/import` with a
multipart `file` field. Requires `people_admin` (HR and admin have it).

Download the template from the Directory page — it is generated from the
importer's own column list, so it cannot drift out of date. Columns:

```
emp_code, name, email, department, designation, role_band,
manager_email, date_of_joining, status
```

Notes that save time:

- `manager_email` must match another row's `email`, or an employee already
  in the system. This is what builds the reporting line every team screen
  depends on.
- Upload without `?commit=1` first for a dry run — you get a per-row
  validation report and nothing is written.
- Legacy `.xls` is rejected with a clear message. Re-save as `.xlsx`.
- **Known bug:** an `.xlsx` containing *cell comments* fails the import
  with a 500. Strip comments before uploading (Review → Delete all
  comments in Excel).
- Sample files to try: `tools/sample-employees.csv`,
  `tools/sample-employees.xlsx`.

### 4.4 Give the test users roles and passwords

Importing an employee does **not** create a login. Two separate steps, both
in **People Hub → Directory** (or by API), both requiring `people_admin`:

| What | Where | API |
|---|---|---|
| Set the permission bundle | Directory → the person → Role | `PUT /api/v1/employees/:id/role` |
| Set a login password | Directory → the person | `POST /api/v1/employees/:id/credentials` |

Valid roles and what they get (`server/migrations/002-default-permission-bundles.js`):

| Role | Permissions |
|---|---|
| `employee` | `pms_self`, `engagement_take`, `people_view` — the default when no row exists |
| `manager` | the above + `pms_team_eval` |
| `hod` | the above + `pms_hod` |
| `hr` | `pms_self`, `pms_admin`, `pms_team_eval`, `pms_hod`, `engagement_admin`, `engagement_take`, `people_admin`, `people_view`, `letters_admin`, `pms_compensation` |
| `admin` | `*` — everything |

For a demo you want at least one of each: an `employee`, their `manager`,
and an `hr`. The reporting line comes from `manager_email` in the import,
not from the role.

### 4.5 Open a performance cycle

**Cycles** (HR Admin section) → New PMS Cycle. Needs `pms_admin`.

`name` and `fiscal_year` are required. The rating scale defaults to five
letter grades, A+ down to C (values 5–1).

A cycle moves through phases in this order, and each phase is what unlocks
the corresponding screens:

```
draft → kra_open → growth_planning → mid_year_review → self_appraisal
      → manager_eval → hod_eval → calibration → publish → closed
```

Advance it from the same page. To demonstrate KRA entry you need
`kra_open`; for the self-appraisal, `self_appraisal`; and so on. **A screen
that looks empty or read-only is usually the phase, not a fault** — the app
says which phase a feature opens in.

### 4.6 Load KRAs

**KRA Overview** (HR Admin) → download the `.xlsx` template, fill it, upload
it. The template's headers are the client's own KRA sheet format:

```
employee_email | Parameters | KRA (S.M.A.R.T GOALS) | KPIs (Measuring Metrics & Data Source) | Weightage | Comments
```

- `Parameters` groups KRAs under a heading (Financial, Project / Process,
  Customer, People). Filled once per group, blank down the rest — the same
  way the source workbooks do it.
- Weightages must total exactly 100 per employee.
- Upload without `?commit=1` for a dry run first; you get a per-row report.

Employees can also enter their own KRAs on **My KRAs** during `kra_open`.

## 5. Verification checklist

Work through this before handing the environment over. Each line is a
thing that has actually broken in a real deploy.

- [ ] `GET /api/v1/health` returns `{"ok":true,...}`
- [ ] The frontend loads and does **not** show network errors in the
      browser console (if it does, `VITE_API_URL` is wrong — §3)
- [ ] You can log in as the bootstrapped admin
- [ ] **Hard-refresh a deep URL** such as `/admin/cycles`. It must load,
      not 404. This is the SPA rewrite in `render.yaml`; clicking around
      inside the app works even when the rewrite is broken, so this can
      only be caught by refreshing
- [ ] The Directory lists the imported employees with their managers
- [ ] Log in as a `manager` test user and open **Team KRA Sheets** — their
      reports appear
- [ ] A cycle exists and its phase is where you expect
- [ ] If demonstrating AI: one AI button returns a draft rather than a 503

## 6. Local development

Postgres, the API and the Vite dev server, run directly. No Docker.

```bash
# 1. Postgres 16 with an empty database, then:
cd server
DATABASE_URL="postgres://user:pass@localhost:5432/apms" \
DATABASE_SSL=false \
JWT_SECRET=dev-only-secret \
TENANT_SLUG=dev \
AUTH_DEV=true \
PORT=8080 \
node index.js          # migrations run on boot

# 2. In another shell:
cd frontend
npm install
npm run dev            # http://localhost:5173, proxies /api to :8080
```

`DATABASE_SSL=false` matters locally — `server/core/db.js` defaults to SSL
on, which a local Postgres will refuse.

Then bootstrap an admin against `http://localhost:8080` exactly as in §4.1.

Tests:

```bash
cd server
DATABASE_URL="postgres://user:pass@localhost:5432/apms_test" npm test
```

Tests skip cleanly without `DATABASE_URL`, so `npm test` alone passes
without proving anything — set the variable.

The suite runs one file at a time (`--test-concurrency=1` in the `test`
script). That is not a performance choice: every test file shares the one
database in `DATABASE_URL`, so running them in parallel — Node's default
— makes them tread on each other's rows and fail differently on each
run. Two runs of the same unmodified code produced 27 and 29 failures
with different test names; serially the same code is 376/376.

> The old `deploy/docker-compose.yml` never worked: it declared
> `build: ../server` when no `Dockerfile` existed. It has been replaced by
> a real stack at `deploy/docker/`, and there is now a full EC2 runbook —
> both the systemd and the Docker path — in [`deploy/README.md`](deploy/README.md).

## 7. AI features (optional)

Every AI feature is gated on one environment variable, `ANTHROPIC_API_KEY`.

**Without it:** each AI endpoint returns a clean `503 Agentic features are
not configured on this instance`, and nothing else in the app is affected.
The AI is additive, never load-bearing — KRAs, appraisals, ratings and
reports all work fully without it.

**With it:** set the value in the Render dashboard on the
`agentic-pms-api` service. It is declared `sync: false` in `render.yaml`,
which means Render prompts for it once, stores it, and preserves it across
every later Blueprint sync. **Never give it a `value:` in `render.yaml`** —
that would commit a live key to the repository and re-apply it on every
sync.

`AI_MODEL` selects the model (`claude-opus-5` in `render.yaml`; the code
default is a generation behind). Not a secret.

Two AI features have preconditions worth knowing before you demo them:

- **Google Meet is deliberately not connected.** The meeting panel names it
  as a not-yet-available provider. The working path is pasting a meeting
  link and a transcript by hand.
- **The HR-only 7-parameter meeting analysis cannot currently run.** It
  requires the employee's recorded consent for AI use of meeting
  recordings, and there is no screen in the application to give that
  consent. The API exists (`PUT /api/v1/consent/me`) but no UI calls it.
  Do not put this on a demo script without checking first.

## 8. Free-tier limitations — read before UAT

These are properties of the Render plans, not faults in the application.

**Free web services sleep after 15 minutes idle.** The next request wakes
them, taking 30–60 seconds. A demo that starts with a long pause is this,
not a hang. It also means the daily reminder sweep (a `setInterval` in
`server/index.js`) does not keep a strict 24-hour clock — it re-runs at
every boot instead, so it still fires, just not predictably. To trigger it
on demand: `POST /api/v1/pms/connects/check-reminders` (HR only).

**Free Postgres is not durable, and this is the one that bites.** Render
removes free databases at the end of their trial window, and the free tier
takes **no automatic backups**. Everything is in that database — the
tenant, every employee, every cycle and rating, and the evidence and
closure-letter *file bytes* (migration 013 stores uploads in Postgres, not
on disk). When the window closes it is all gone, with no restore path.

> Fine for UAT on disposable data. **Not** a place to accumulate anything
> you would mind re-entering, and never where real employee records live.

Check the current expiry window on Render's pricing page before planning
UAT dates, and move to a paid plan before any real data goes in.

## 9. Before this becomes production

The PoC configuration is deliberately permissive. Do not carry it into
production.

| Item | Now | Needs to be |
|---|---|---|
| **Authentication** | `AUTH_DEV="true"` — email + password against `core.local_credentials`. A break-glass mechanism, not real authentication | The client's IdP via OIDC. **Not built.** Budget for it |
| **`AUTH_DEV`** | `"true"` in `render.yaml` | `"false"`. Note a fixed `value:` in `render.yaml` is re-applied on every sync and silently overwrites any dashboard change — so change it in the file, not the dashboard |
| **CORS** | `app.use(cors())` — every origin allowed | Restricted to the frontend origin |
| **All three plans** | `free` | Explicit paid plans: always-on API, durable backed-up database |
| **Error messages** | Roughly 150 sites return the raw exception message to the client | Sanitised for callers, complete in logs |
| **Database backups** | None | Paid tier's automatic backups, plus a tested restore |

No code changes are needed for the plan and CORS items — they are
configuration.

## 10. Troubleshooting

Ordered by how often each has actually happened.

**Every API call fails; console shows `ERR_NAME_NOT_RESOLVED`**
`VITE_API_URL` is wrong or still points at another deployment. §3. Fix the
literal in `render.yaml` and let the frontend **rebuild** — a dashboard
change alone will not do it, because Vite inlines the value at build time.

**Login rejected in the browser but the same credentials work in `curl`**
Almost always CORS. Check the browser console for a CORS error rather than
an auth error, and confirm the API redeployed after the last change.

**A deep link 404s on refresh, but works when clicked**
The SPA rewrite in `render.yaml` is missing or not applied. Clicking
navigates client-side and never hits Render, which is why this hides during
casual testing.

**Blueprint sync fails: "cannot have more than one active free tier database"**
The workspace's single free Postgres slot is taken. §2.

**The app loads but is completely empty after working before**
`TENANT_SLUG` changed. The old data is intact under the old slug — put the
original value back. §2.

**API will not start**
Read the Render logs. A failed migration deliberately kills the boot rather
than serving a half-migrated schema. The log names the migration.

**First request after a quiet period takes 30–60 seconds**
Free-tier cold start. §8.

**An AI button returns 503**
`ANTHROPIC_API_KEY` is not set on the API service. §7.

**A screen is empty or read-only and you expected to edit it**
Check the cycle's phase. Most screens are gated to a phase and say which
one they open in. §4.5.

## 11. Reference

**Endpoints used in this document**

| Purpose | Endpoint |
|---|---|
| Health | `GET /api/v1/health` |
| Is bootstrap available | `GET /api/v1/setup/status` |
| Create first admin | `POST /api/v1/setup/bootstrap-admin` |
| Log in | `POST /api/v1/auth/dev-login` |
| Employee import template | `GET /api/v1/employees/import-template.csv` |
| Import employees | `POST /api/v1/employees/import` (`?commit=1` to write) |
| Set a role | `PUT /api/v1/employees/:id/role` |
| Set a password | `POST /api/v1/employees/:id/credentials` |
| KRA bulk template | `GET /api/v1/pms/hr/kra-sheet/bulk-upload-template.xlsx` |
| KRA bulk upload | `POST /api/v1/pms/hr/kra-sheet/bulk-upload` (`?commit=1`) |
| Run reminder sweep now | `POST /api/v1/pms/connects/check-reminders` |

All API paths are prefixed `/api/v1`.

**Environment variables**

| Variable | Required | Set by | Notes |
|---|---|---|---|
| `DATABASE_URL` | yes | Render (`fromDatabase`) | Never set by hand |
| `JWT_SECRET` | yes | Render (`generateValue`) | Never set by hand |
| `TENANT_SLUG` | yes | `render.yaml` | One-shot. §2 |
| `AUTH_DEV` | for PoC login | `render.yaml` | `"false"` for production |
| `ANTHROPIC_API_KEY` | no | Render dashboard | `sync: false`. Never in git |
| `AI_MODEL` | no | `render.yaml` | Not a secret |
| `DATABASE_SSL` | local only | shell | `false` for local Postgres |
| `PORT` | no | Render | Defaults to 8080 locally |

The API refuses to start without `DATABASE_URL`, `JWT_SECRET` and
`TENANT_SLUG`, naming which are missing.
